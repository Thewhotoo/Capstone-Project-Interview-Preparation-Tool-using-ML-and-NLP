## 1. What this project is

An AI-driven "Resume Discussion" platform: a candidate uploads a resume, Gemini parses it into a structured `CandidateProfile`, a deterministic Planner picks discussion topics, a Conversation Engine phrases questions and holds the interview, and an Evaluation Engine scores each answer. All of this is **built, tested, and working** (Phases 1–3 below). On top of that live system, a second, parallel track has been built: a fully-specified **ML research program** for eventually training a real evaluator model, plus a first slice of **implementation** for that program — the Stage A Synthetic Dataset Generation Pipeline, completed in this session.

## 2. Architecture governance model — READ BEFORE CHANGING ANYTHING

This project is run "architecture-first, implementation-second," with a strict discipline that must continue:

1. Every subsystem starts as an **RFC** (chat-authored design document), reviewed and explicitly **approved and frozen** before any code is written.
2. Implementation must **faithfully follow the frozen RFC** — no redesign, no simplification, no "while I'm here" changes, no unauthorized new abstractions.
3. **If implementation reveals a real tension with a frozen RFC, STOP, document the issue, justify it, and wait for approval before changing anything.** Do not silently redesign.
4. Strict separation-of-concerns boundaries are enforced **by tests**, not just by convention — see `test_evaluation_engine.py`'s and `test_synthetic_generation_pipeline.py`'s import-graph AST assertions for the pattern to replicate whenever a new subsystem is added.
5. Determinism discipline: use `zlib.crc32` for any pseudo-random-but-reproducible choice — **never** Python's `hash()` (salted per-process) and **never** the `random` module in code paths that must replay identically.
6. Frozen/immutable Pydantic models everywhere a record must outlive the code that produced it: `model_config = ConfigDict(frozen=True)`, tuples (never lists) for nested collections, an explicit `..._SCHEMA_VERSION` constant, and a `model_validator(mode="after")` that enforces every invariant at construction time (never left to caller discipline).
7. Taxonomy design rule, applied consistently: **closed** taxonomies (fixed, small, not expected to grow) are Python `Enum`s — e.g. `ReasoningType`, `QuestionCategory`, `UnitStatus`, `ConceptObservationStatus`, `QualityTier`, `ContradictionType`, `ProvenanceSource`. **Open** taxonomies (registries expected to grow over time) are plain-string constants on a class, extended by adding new string values, never a schema change — e.g. `MissingReasoningCategory`, `ConfidenceSource`.
8. **"Never invented, always grounded"** — the single most-repeated rule in this codebase. Every phrasing, evidence citation, expected concept, suggested improvement, and now every synthetically generated answer must trace back to the actual `QuestionSpecification.grounding` (or the candidate's own resume-derived profile). Nothing is ever invented to fill a gap.
9. **Phased implementation** (explicit standing preference from the user): break implementation into small phases, run/test after each phase, stop if anything looks unstable before continuing.

### 3d. Coverage/Batch Strategy — IMPLEMENTED THIS SESSION

`coverage_strategy.py` + `test_coverage_strategy.py` (19 tests). Implements Dataset Generation RFC §3 exactly as the user restated it this session (full text preserved in this session's chat; not re-copied here — ask the user to re-paste RFC §3 if a future session needs the verbatim source, same discipline as §3b for the other RFCs).

**Key design decisions:**
- **Zero modification to `synthetic_generation_pipeline.py`.** `generate_batch`'s existing `tier_cycle` parameter already resolves via `tier_cycle[index % len(tier_cycle)]`; handing it a tier tuple exactly as long as `units` makes every index resolve to its own assigned tier. `CoverageStrategy.plan_batch` produces `CoveragePlan(units, quality_tiers)` — call `generate_batch(plan.units, tier_cycle=plan.quality_tiers, ...)`. `DEFAULT_TIER_CYCLE` is left in place (still tested, still the standalone fallback for callers not using a CoverageStrategy) — this module supersedes its *role* as the production coverage policy, not its existence.
- **Follow-up ratio — a real schema gap, resolved without touching frozen schemas:** none of `BatchUnit`/`GenerationRecipe`/`TrainingExample` represent "this originated as a follow-up question" anywhere. Rather than adding a field to a frozen model, `CoverageUnit.is_follow_up` (new, non-frozen, pool-input-only type defined in `coverage_strategy.py`) carries the flag — set by the caller, never invented, never persisted onto a `TrainingExample`. If follow-up provenance needs to live on `TrainingExample` itself, that's a new RFC decision for the user, not something decided silently here.
- **Off-topic/contradiction counts are carved out of `batch_size` first**, independently of the 20/20/20/20/20 core-tier split (RFC: both are "independent of quality," must not skew toward weak/poor). Remainder from the core-tier integer allocation goes to Excellent first, then down the list, per RFC wording.
- **Reasoning-type coverage** via `_BucketCursor`: round-robins `ReasoningType`'s declared enum order (restricted to types present in the pool), then round-robins within each type by original pool order — a monotonic cursor that never resets across the batch, which is this implementation's concrete reading of the RFC's "maximize diversity before repeating combinations."
- **All shuffling/allocation is `zlib.crc32`-keyed** (a stable sort over original indices, never Python's `random`) — same determinism discipline as `generation_recipe.py`.
- Expected-concept/missing-reasoning *observation-state* coverage (Demonstrated/Superficial/Omitted; Present/Absent) is **not** separately tracked in `coverage_strategy.py` — per the RFC's own wording, the exact state is `GenerationRecipe`'s probabilistic call conditioned on the tier assigned here; spreading tier assignments and pool-unit repeats across the batch (which this module does) is what makes eventual full coverage of every state likely across a sufficiently large batch, without CoverageStrategy duplicating that sampling logic itself.

### 3e. DatasetManifest + ReviewEvent subsystem — IMPLEMENTED SESSION 3

`dataset_manifest.py` + `test_dataset_manifest.py` (26 tests). Implements the Dataset Manifest RFC (restated fresh by the user this session — full text lived only in a prior chat, same discipline as §3d). Design was proposed in full (analysis, architecture, integration story, ambiguities) and **explicitly approved with adjustments before any code was written** — a design-review checkpoint the earlier milestones didn't go through as formally, worth repeating for future large subsystems.

**Approved design, as built:**
- **`DatasetManifest` never owns/duplicates `TrainingExample` objects** — only `example_ids: tuple[str, ...]` (membership by reference) plus aggregate statistics (`tier_distribution`, `label_source_distribution`, `generator_provenance`, `review_summary`) computed once at assembly time. It is a frozen snapshot describing a dataset, not a container of it.
- **`assemble_manifest(examples, dataset_version, review_log=None, parent_dataset_version=None, allow_reversioning=False) -> (DatasetManifest, stamped_examples)`** stamps `dataset_version` onto each `TrainingExample` via nested `model_copy` (never in-place mutation — frozen models stay frozen; a *new* object is returned) and returns the stamped examples as its second return value, since the manifest itself never embeds them.
- **Whether an already-versioned example can be re-stamped into a new lineage is a policy owned by `assemble_manifest`, not an assumption in the `DatasetManifest`/`TrainingExample` models** — `allow_reversioning: bool = False` defaults to raising `AlreadyVersionedError`, but passing `True` is a supported, tested path (`test_allow_reversioning_permits_re_stamping`). This was an explicit correction from the user to the original proposal (which had suggested baking in an unconditional reject).
- **`ReviewEvent.event_type` is an open string (`ReviewEventType` constants: `approved`/`rejected`/`flagged`/`relabeled`), not a closed `Enum`** — the Labeling Operations RFC (still design-only) owns the real vocabulary; freezing one now would risk a forced schema change later. Same closed-vs-open reasoning already used for `MissingReasoningCategory`/`ConfidenceSource`.
- **`ReviewEventLog` is the controlled-mutation wrapper** (same `UnitLifecycleState`/`CoverageTracker` precedent): `record(...)` only ever appends; there is no `remove`/`update`/`clear` method anywhere on the class — append-only is structural.
- **`dataset_version` stays an opaque, caller-supplied string** — no format/scheme invented, matching `generation_batch_id`/`recipe_id` elsewhere.
- **`supersede(manifest, new_dataset_version) -> DatasetManifest`** is the forward-lineage half (also `model_copy`-based); refuses to re-supersede an already-superseded manifest and refuses self-supersession.
- **Strict independence, enforced by an AST import-boundary test** (same pattern as `test_synthetic_generation_pipeline.py`): `dataset_manifest.py` imports nothing but `training_example.py` + stdlib — zero dependency on `synthetic_generation_pipeline.py`, `coverage_strategy.py`, any `generation_*`/`prompt_*` module, or any Evaluation/Conversation/Planning module. A manifest describes a dataset of `TrainingExample`s regardless of where they came from.

### 3f. Labeling Operations subsystem — IMPLEMENTED SESSION 4

`labeling_operations.py` + `test_labeling_operations.py` (25 tests). No RFC prose ever existed for this one, not even in prior chat history (unlike §3d/§3e, which restated real chat-authored RFCs) — the user explicitly asked for a fresh design proposal grounded in the existing codebase and established principles, which was reviewed and approved with 5 named decisions before any code was written.

**Approved decisions, as built:**
1. `LabelingConfig.required_agreement_reviewers` defaults to **2**.
2. A reviewer may revise their own verdict — `compute_review_state` folds each reviewer's ordered event history and keeps only their **latest** `approved`/`rejected` event.
3. Any `flagged` event forces `ReviewState.NEEDS_ADJUDICATION` immediately, regardless of existing agreement, until an `adjudicated` event resolves it (adjudication is checked first in the fold and is terminal/authoritative).
4. `ReviewerRegistry` roles are **not** permanently fixed: `register(...)` sets an initial role (raises `DuplicateReviewerError` on a second call for the same id), `update_role(...)` supports promotions on an already-registered reviewer (raises `UnknownReviewerError` otherwise). No role-change history is kept — simple, deterministic dict operations only.
5. Only **`ANNOTATOR`** and **`ADJUDICATOR`** roles exist — no `QA_LEAD`, deliberately deferred to a future, separately-scoped RFC.

**Key architectural points:**
- **`ReviewState` is always derived, never stored** — `compute_review_state(events, config)` is a pure fold over `ReviewEventLog.events_for(example_id)`'s output; there is no new mutable per-example state anywhere. Same "the log is the single source of truth" philosophy `DatasetManifest.review_summary` already established.
- **`LabelingReviewEventType` (`needs_adjudication`, `adjudicated`) extends `dataset_manifest.ReviewEventType`'s vocabulary additively** — `dataset_manifest.py` is completely untouched; this is exactly the "real vocabulary owner" that module's docstring said would come later.
- **`record_review(...)` is the only place this module writes to a `ReviewEventLog`**, and role-gates `adjudicated` events against a `ReviewerRegistry` (`UnauthorizedReviewActionError` if missing/wrong role) — this is where governance is actually enforced. Still just calls `ReviewEventLog.record` underneath; the append-only guarantee is unchanged.
- **`ReviewerMetrics`/`compute_reviewer_metrics` are derived-only** (pairwise agreement/disagreement counts against other reviewers' latest verdicts on the same example) — never a separately stored counter.
- **Discovered during implementation, not a deviation:** `TrainingExample._synthetic_presence_matches_source` (already frozen, from the original Dataset Design RFC) forbids a `SYNTHETIC`-provenance example from ever having `label_source="human_reviewed"` — correctly, since a synthetic example's labels are its ground truth by construction. `apply_relabel` therefore only accepts a `REAL_SESSION`-provenance example, raising `ValueError` otherwise, rather than letting `model_copy` silently build a `TrainingExample` that would fail its own validator if ever reconstructed. No schema was changed to resolve this — it was already correctly enforced; `apply_relabel` just respects it explicitly.
- **`apply_relabel` reconstructs `TrainingExampleLabels` via its normal constructor** (`TrainingExampleLabels(**{...})`), not `model_copy` — `model_copy` does not re-run validators, and this project's rule is that every invariant must be enforced at construction time, never left to caller discipline.
- **Strict independence, enforced by an AST import-boundary test** (same pattern as `test_dataset_manifest.py`/`test_synthetic_generation_pipeline.py`): `labeling_operations.py` imports only `training_example.py` + `dataset_manifest.py` + stdlib.

### 3h. Model-Implementation Layer — IMPLEMENTED SESSION 6

Five new modules, giving session 5's infrastructure-only `training_experimentation.py` a real, working model behind it for the first time. No RFC text existed for this layer either — proposed fresh from the codebase, with three genuine ambiguities resolved by explicit user decision before any code was written, plus one further architectural refinement.

**Approved decisions (read before extending this layer):**
1. **Ordinal regression is per-dimension**, not just at the overall-grade level — each of the 12 dimensions in `reasoning_dimension_relevance.ALL_DIMENSIONS` gets its own CORAL ordinal head. `DimensionLabel.score` (a continuous [0,1] float) is binned into the same 5-tier scale `HeuristicEvaluator._grade` already uses (`model_dataset.score_to_tier`, cutpoints 0.80/0.60/0.40/0.25 — duplicated intentionally, not imported).
2. **Expected Concepts and Missing Reasoning use DIFFERENT architectures, deliberately**: Expected Concepts get a separate true cross-encoder pass per concept (`ConceptObservationHead`, one forward pass per `(answer, concept)` pair) because concepts are dynamic/open (`expected_concepts_registry.py`'s growable table). Missing Reasoning uses a SINGLE shared multi-label head off the main pooled representation (`MissingReasoningHead`) because its 11-category set (`model_heads._MISSING_REASONING_CATEGORIES`) is fixed-in-practice — this was an explicit architectural refinement from the user correcting the original proposal (which had suggested a per-category cross-encoder pass for both).
3. **Confidence is derived analytically, never trained**: `coral_confidence` computes `1 - mean_binary_entropy` directly from each CORAL head's own logits. No confidence head, no invented ground-truth label (there is none anywhere in `TrainingExampleLabels`).
4. **`confidence_source="model_derived"`** is used as a raw string literal (`model_evaluator._CONFIDENCE_SOURCE_MODEL_DERIVED`), NOT added as an attribute on `evaluation_result.ConfidenceSource` — that class's own docstring says new sources are added "on evaluator implementations," never by editing that shared module. `evaluation_result.py` is untouched.
5. **CORAL (Cao et al.)** is the ordinal regression technique — rank-consistent by construction (shared linear projection + monotonically non-increasing biases), not just encouraged by the loss.
6. **CLS pooling is the default** (`BackboneConfig.pooling="cls"`); mean-pooling is implemented and selectable but not the default.
7. **Testing uses the REAL tokenizer with a tiny, randomly-initialized DeBERTa-v2 body** (`model_backbone.build_tiny_random_encoder`/`build_tiny_random_backbone`) — never the real ~700MB pretrained weights in unit tests. A one-time `sentencepiece` install was required (DeBERTa's tokenizer needs it) — now in `requirements.txt`. Full pretrained-weight integration testing is explicitly left as future work, not built here.
8. **Training loop is minimal by design** (`model_heads.train_model`): fixed epoch count, single AdamW optimizer, no LR scheduler/mixed precision/distributed training/hyperparameter search/early stopping — all explicitly deferred.
9. **Variable-length concept batching is flattened** with an index-back-to-example mapping (`model_dataset.collate_fn`'s `concept_example_index`), not padded to a per-batch max — chosen as "simplest correct implementation" per the user's own framing of that decision as an implementation detail.

**Module structure and what each owns:**
- `model_backbone.py` — `BackboneConfig`, tokenizer pipeline, `CrossEncoderBackbone` (ONE shared encoder; every head is a separate forward pass through it with a different text-pair — this is what "cross-encoder" means here), plus the test-only tiny-backbone builders.
- `model_heads.py` — `CoralOrdinalHead`/`coral_targets`/`coral_loss`/`coral_predict`/`coral_confidence`, `DimensionOrdinalHeads` (all 12 always computed; masking happens at loss/read time via `reasoning_dimension_relevance.relevant_dimensions`, reused not reinvented), `ConceptObservationHead`, `MissingReasoningHead`/`missing_reasoning_loss` (severity loss masked to `presence_target==1`, mirroring `ReasoningCategoryTarget`'s own existing invariant), `MultiTaskModel`, `compute_batch_loss`, `train_model`.
- `model_dataset.py` — `TrainingExampleDataset`/`collate_fn`/`build_dataloaders`; consumes an ALREADY-COMPUTED `training_experimentation.DatasetSplit` — never re-derives a split. Ground truth for every head comes from `TrainingExample.labels` (never `.synthetic`'s recipe targets, which are Stage-A-specific and absent for real-session examples).
- `model_checkpoint_io.py` — `save_checkpoint_artifact`/`load_checkpoint_artifact`: the one place a real filesystem path becomes `Checkpoint.artifact_uri`'s value. `training_experimentation.py` is never modified and never imports torch.
- `model_evaluator.py` — `TrainedEvaluator` (implements the UNCHANGED `evaluator.Evaluator` Protocol — no base class, no interface change), reusing the off-the-shelf NLI contradiction-detection technique (frozen ML Architecture RFC decision: reused, never fine-tuned) reimplemented locally rather than importing `heuristic_evaluator.py`; `promote_trained_model` — thin glue asserting `PromotionDecision.approved` then calling the UNCHANGED `evaluator_registry.register_evaluator`.

**Verified end-to-end** (both as a manual smoke test and as `test_model_evaluator.py`'s promotion tests): `build_dataloaders` → `train_model` → `save_checkpoint_artifact` → `assemble_checkpoint` (unmodified) → `load_checkpoint_artifact` → `TrainedEvaluator` → `run_benchmark` (unmodified) → `decide_promotion` (unmodified) → `promote_trained_model` → `evaluator_registry.get_active_evaluator()` returns the trained model. Zero modification to `training_experimentation.py`, `evaluator.py`, `evaluator_registry.py`, `evaluation_request.py`, or `evaluation_result.py`.

**Open/closed taxonomy note worth remembering**: `_MISSING_REASONING_CATEGORIES` (11 items) is a FIXED set required by the shared multi-label head's fixed output dimension, even though `evaluation_result.MissingReasoningCategory` is nominally an OPEN, growable registry. ### 3l. Experiment 0 — Reproducibility (research-validity milestone) — SESSION 10

Preceded by a full 6-item experimentation plan (research objective, variables to isolate vs. fix, metrics beyond QWK, minimum experiment set with runtime estimates, validity threats, execution order) presented for approval before any code — the user approved the plan but authorized **only** Experiment 0 (reproducibility) for this session, explicitly deferring Experiments 1+ (all real training/benchmarking) until Experiment 0 is validated. **No dataset was generated and no model was trained this session** — every check below uses the tiny random-init test backbone, never real `deberta-v3-base` weights.

**What changed (both additive, backward-compatible — `None` default preserves all prior behavior exactly):**
- **`model_heads.train_model(..., random_seed: Optional[int] = None)`** — when given, calls `torch.manual_seed(random_seed)` as the very first action, before `MultiTaskModel` is constructed. Covers: freshly-initialized head-layer weights (`DimensionOrdinalHeads`/`ConceptObservationHead`/`MissingReasoningHead` — the backbone's own pretrained weights are already deterministic, loaded from a checkpoint, not randomly initialized) and dropout masks throughout training.
- **`model_dataset.build_dataloaders(..., seed: Optional[int] = None)`** — when given, the TRAIN loader (the only one with `shuffle=True`) is built with an explicit `torch.Generator().manual_seed(seed)` rather than relying on PyTorch's implicit global RNG state. Deliberately independent of `train_model`'s own seeding, so reproducibility doesn't depend on the exact order the two modules happen to consume global state.
- **`run_first_experiment.py`/`run_second_experiment.py`** — both now actually pass `random_seed=RANDOM_SEED` to `train_model` and `seed=RANDOM_SEED` to `build_dataloaders`. This closes the exact gap flagged repeatedly since session 7 (§3i item 1, §3j, §3k): `ExperimentConfig.random_seed` was always *recorded* as metadata but never *applied* anywhere. `run_third_experiment.py` doesn't call either function (generation-only scope) — nothing to wire there.

**How reproducibility is now guaranteed**: given the same `random_seed` passed to both `build_dataloaders` and `train_model`, and the same starting model weights (same backbone, same construction path), a training run's shuffle order, weight initialization, and dropout behavior are all deterministic — repeated runs produce **bit-identical trained weights** (`torch.equal` on every tensor in `state_dict()`, not just "close"). This was verified two ways:
1. **7 new unit tests** (`test_model_heads.py`'s `TestTrainModelReproducibility`, 4 tests; `test_model_dataset.py`'s 3 new shuffle-seeding tests) — same seed -> identical results; different seed -> different results; unseeded calls still work (no crash, no forced determinism).
2. **One integrated, end-to-end empirical check** (script-level, not a permanent test file — combined `build_dataloaders` + `train_model` together, 2 epochs, tiny backbone): two full runs with `random_seed=42` (and identically-seeded backbone construction beforehand) produced **bit-identical `state_dict()`s**; a run with different seeds produced **different weights**. Confirmed the fix works holistically, not just in isolated unit tests.

**What is explicitly NOT covered by this fix (honest limitations, not oversights)**:
- **CUDA nondeterminism** is untested and likely irrelevant — this environment is CPU-only; `torch.manual_seed` alone is what CPU determinism needs, no `torch.use_deterministic_algorithms` was added (would risk breaking DeBERTa ops lacking deterministic CPU kernels, for no benefit in a CPU-only environment).
- **No repeated-trials/variance reporting** — reproducibility means "the same seed always gives the same result," not "we know how much results vary across different seeds." That remains an accepted limitation of the whole experimentation plan (flagged in the plan's §5, item 2), not something this milestone was meant to solve.
- **Real `deberta-v3-base` weight loading remains deterministic regardless of seed** (loaded from a fixed checkpoint) — seeding only matters for the newly-initialized head layers and dropout, exactly as documented in `train_model`'s updated docstring.

Full suite: **726 passed, 19 subtests passed, 0 regressions** (was 719+7 new tests). Ready to proceed to Experiment 1 (anchor: trained vs. untrained vs. trivial baselines + epoch curve) once approved — see the approved experimentation plan (session 10, chat-only, not yet written to disk) for its exact design.

## 5. Key architectural decisions made this session (and why)

- **Quality tier is a pipeline input, not something `generation_recipe.py` samples.** The Dataset Generation RFC assigns tier/mode selection across a batch to a separate "coverage strategy" component (still design-only, RFC §3). Rather than inventing that component's policy, `synthetic_generation_pipeline.generate_batch` uses a fixed, documented `DEFAULT_TIER_CYCLE` as a reasonable stand-in, clearly labeled as such — **this is a placeholder, not the RFC's real coverage strategy**, and should be revisited if/when that RFC section gets implemented for real.
- **Contradictory-tier recipes still sample concept/reasoning targets** (using the GOOD-tier distribution) — this directly implements the Promptbook RFC's explicit statement that a contradictory answer is "otherwise fluent, plausible-quality prose, independent of quality tier."
- **Off-topic recipes carry zero concept/reasoning targets by construction** (enforced by a Pydantic validator on both `GenerationRecipe` and `TrainingExampleSyntheticMeta`) and `prompt_assembler.assemble_prompt` additionally suppresses those two controllers' output at assembly time if a recipe is somehow off-topic — belt-and-suspenders enforcement of the Promptbook's override rule.
- **The hallucinated-technology check is a small, explicitly-labeled heuristic registry** (`_KNOWN_TECHNOLOGY_VOCABULARY` in `generation_validation.py`), not a claim of complete coverage — same honesty pattern already established for `HeuristicEvaluator`'s marker-based dimension scoring.
- **Reasoning-mismatch markers are deliberately duplicated**, not imported from `heuristic_evaluator.py` — preserving the same "deliberate independence between subsystems" pattern `heuristic_evaluator.py` itself documents relative to `discussion_engine.py`. Do not "clean this up" by sharing the marker lists; it's intentional.
- **Reject-and-regenerate always re-samples a fresh recipe** (via a salted `recipe_id`, e.g. `"{recipe_id}::attempt2"`) rather than reusing the previous attempt's recipe/output — verified by `test_synthetic_generation_pipeline.py::test_each_attempt_uses_a_distinct_recipe`. Never patch a rejected output.
- **`dataset_version` on `TrainingExampleMetadata` is always `None` from this pipeline.** It gets stamped later by DatasetManifest assembly (still design-only, per the Dataset Manifest RFC) — the generator is explicitly forbidden from knowing/assigning it, preserving the "generator does not generate DatasetManifests" separation-of-responsibility rule from the task.
